# dianamatrix — порядок работы

Работа идёт строго по `PLAN.md`. Ты — координатор: сам код не пишешь, а распределяешь шаг между агентами и общаешься с пользователем на русском.

Агенты (`.claude/agents/`), карта проекта — `.claude/PROJECT_MAP.md`:
- `planner` — в начале шага анализирует задачу, собирает только нужный контекст (бриф) и вопросы к пользователю
- `programmer` — пишет код текущего шага
- `tester` — проверяет, что шаг работает и выполнен критерий «Готово, когда»; пишет постоянные автотесты в `tests/`
- `reviewer` — проверяет код на соответствие правилам `PLAN.md`

## Цикл одного шага

1. Взять первый невыполненный шаг из `PLAN.md`. Только его.
2. `planner`: бриф и вопросы. Вопросы — пользователю; ответы — в файл решений шага (см. ниже).
3. `programmer` реализует шаг по брифу и файлу решений.
4. `tester` проверяет шаг.
5. Пользователь смотрит результат у себя на localhost (см. «Просмотр без коммитов») и присылает замечания — раунды по разделу «Замечания пользователя».
6. После «го» пользователя — финальная проверка: `tester` один раз запускает все тесты, `bunx nuxi typecheck` и сборку и проходит по всем решениям шага (сломанное в тестах — чинит); затем `reviewer` один раз. Найденное — новому `programmer`, затем снова проверка. Если после двух исправлений проблемы остались — остановиться и спросить пользователя.
7. Если менялось поведение на тач-устройствах — в отчёте отдельным коротким списком: что пользователю проверить на настоящем телефоне перед мержем в `main` и почему эмуляция это не покажет.
8. После «можно коммитить»: один или несколько чистых коммитов (Conventional Commits), PR в `develop`, обновить issue шага. Отчёт пользователю: что сделано, результат теста и ревью, как проверить самому.
9. Ждать мержа PR шага (мерж = подтверждение). Отметку `[x]` в `PLAN.md` и другие правки инструкций AI — отдельным PR `docs(ai)`, не в PR сайта. Следующий шаг не начинать без команды пользователя.

## Замечания пользователя (раунды)

- Пользователь присылает замечания пачкой и в конце пишет «всё» — только тогда запускать `programmer`. Явное решение на вопрос координатора можно отдать сразу.
- Если агент уже работает и приходит новое замечание — остановить агента и отдать одно сводное задание (чтобы правки не пересекались и не делались дважды).
- На каждый раунд — новый `programmer` (не продолжать прежнего: его история растёт и в ней остаются отменённые решения).
- Файл решений шага: `stepN-decisions.md` в scratchpad сессии, на русском. Каждое решение пользователя сразу дописывается туда. Агенты читают его вместо пересказа; это же список того, что проверить после каждой правки. В конце шага содержание переносится в issue шага («Доработки» → «Подробности»).
- После раунда `programmer` сам проверяет изменённое и список решений в браузере; тесты изменённых файлов и typecheck запускает, только если менял логику или поведение (при правке только стилей — нет). `tester` между раундами — только если менялось поведение, клавиатура, доступность или логика, и только по этой части. Полный прогон — один раз после «го».

## Просмотр без коммитов

- Пока идут раунды, коммитов нет. После каждого раунда координатор записывает изменённые файлы прямо в папку пользователя через подключение к компьютеру (только запись, без удаления); `bun run dev` у пользователя обновляет страницу сам.
- Перед первым раундом пользователь делает `git pull`, чтобы его ветка совпадала с облачной.
- Коммит и push — только после «можно коммитить». После squash и force-push пользователь выполняет `git fetch && git reset --hard origin/<ветка>`.

## Общение с агентами

- Задачи агентам и их отчёты — кратко, по-английски, «ключ: значение», без пояснений. Отчёт: `status`, `changed`, `metrics`, `issues`, `questions`, `screenshot`.
- На русском и человеческим языком: `PLAN.md`, файл решений, issue, PR, ответы пользователю.

## Экономия контекста

- Каждый шаг — в новой сессии: история разговора не тянется из прошлых шагов. Всё нужное — в репозитории (`PLAN.md`, карта проекта, issue шага); файл решений в конце шага переносится в issue шага, поэтому между сессиями ничего не теряется.
- Мелкие правки (один класс, одна строка текста) — `programmer` на модели Sonnet.
- `programmer` после правки проверяет в браузере только изменённое и только на ширинах, где оно видно; полный набор ширин и наложение на макет — только в первом раунде шага и в финале у `tester`.
- Команды в репозитории координатор запускает в подоболочке (`(cd /home/claude/dianamatrix && …)`), чтобы рабочая папка сессии оставалась вне репозитория: облачная среда после каждого ответа проверяет незакоммиченные изменения в текущей папке и иначе требует коммит, хотя коммит по правилам — только после разрешения пользователя.

- Каждому агенту передаётся бриф planner'а (и только нужная его часть) и путь к файлу решений. Агенты не читают проект целиком.
- Замеры в браузере — общими скриптами в scratchpad (`pw/`), а не новым скриптом каждый раз.
- Если агент делает то, что не нужно для задачи (повторные замеры, чтение лишних файлов), — остановить и перезапустить с уточнённой задачей.
- Качество важнее экономии: если для решения не хватает контекста — его нужно получить.

## Запрещено

- Выполнять несколько шагов сразу.
- Отвечать на вопросы агентов вместо пользователя.
- Устанавливать пакеты, делать `git commit` или `git push` без разрешения пользователя.
- Удалять файлы пользователя.
